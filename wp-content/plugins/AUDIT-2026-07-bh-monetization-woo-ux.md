# bh-monetization-woo — MAGICAL UX Audit (2026-07-25)

**Scope:** storefront/collection pages, Supporter Tiers admin screen, checkout-adjacent flows (tiers, gifting, wallet top-up, pay-what-you-want, subscription pause/resume), admin screens (tiers config, monetization settings, fraud/debug tools).

**Method / caveat — read this first:** this is a **code-level UX read only**. No live browser or WordPress install was used; there was no walkthrough of an actual rendered page, no click-through of a real checkout, and no rendered-contrast measurement. Every finding below is inferred from template/render-method source (PHP `echo`/heredoc markup, shortcode renderers, and the plugin's own CSS files) and is cited to file:line. Anything about "how this will look/feel" is a reasoned prediction from the markup and CSS, not an observation of a live screen — treat visual/contrast claims as needing a live-render pass to confirm, exactly as flagged in the prior UX-AUDIT-2026-07.md.

Code-quality concerns (naming, DRY, error handling, etc.) are explicitly out of scope — a separate pass already covered that for this plugin.

---

## 1. Supporter Tiers admin screen (`includes/class-tiers.php`)

**Confirmed good / re-confirmed from prior audit:**
- Nests under WooCommerce's own top-level admin menu when WooCommerce is active, falling back to a real top-level menu otherwise (`register_post_type()`, `class-tiers.php:124`: `'show_in_menu' => ... ? 'woocommerce' : true`). Still true in current code — mirrors how real WooCommerce extensions (Subscriptions, Bookings) behave, exactly the pattern the 07-17 note flagged as good.
- The tier list table gets a real, sortable Price column via the shared `OUS_ListTable` helper (`class-tiers.php:73-79`) rather than a bespoke implementation — good design-system discipline (shared component, not a one-off).

**Good, fresh finds this pass:**
- The metabox visually separates "what fans see" (marketing copy — benefits text/list) from "what actually gets enforced" (benefit-key checkboxes) using two distinct headed panels with different background tints (`class-tiers.php:207-235`), plus a live JS-driven warning (`#bhm-no-benefits-warning`, `class-tiers.php:234`, wired by `tier-admin.js`) if a priced tier has zero benefits checked. This is a genuinely well-considered "prevent a silent misconfiguration" pattern — an admin can't accidentally sell a tier that grants nothing without a visible warning.
- Annual pricing shows the monthly-equivalent breakdown and a real "save X%" calculation only when it's a genuine discount (`class-frontend.php:195-202`, mirrored conceptually on the admin side) — avoids a misleading 0%/negative "savings" claim.
- Honest, real-time capability messaging throughout: every field that depends on WooCommerce Subscriptions (annual billing, free trial) explicitly states what happens if Subscriptions isn't active, rather than silently accepting a value it can't honor (`class-tiers.php:178-181`, `192-194`, `237-241`).

**Rough edges:**
- The metabox is a long, single-scroll `<p>`-stacked form (cover image → monthly price → annual price → trial days → benefits panel → enforcement panel → WC product link → version history), all rendered via raw `echo` HTML in one static method (`class-tiers.php:133-256`). It's coherent and well-labeled, but it's a wall of fields on one screen, not a guided one-question-at-a-time flow — acceptable for a WP-native CPT edit screen (matches the stated "default to plain WP admin styling" convention), but worth flagging since "it just works" wizard framing is explicitly the bar for anything wrapping a technical concept, and recurring-billing setup (price + annual + trial, three fields whose actual behavior silently branches on whether a separate paid extension is installed) is arguably that kind of concept.

## 2. Monetization Settings screen (`includes/class-admin.php`)

**Good:**
- The "Get paid" card (`class-admin.php:121-135`, `render_get_paid_card()`) does a **live** check via `BH_Commerce::get_available_payment_gateways()` and renders a real ✅/❌ state rather than a static instructional paragraph — this is a genuine "it just works" instance: validate/confirm in real time rather than accept-and-hope. Green left-border + "Ready to get paid" when a gateway is live, red border + a direct "Set up a payment method →" link into WooCommerce's own guided payments screen when not. This is the single best "it just works" moment in this plugin.
- Explicitly does not reimplement WooCommerce's own payment-gateway configuration — thin honest launcher, consistent with the "wrap it, don't rebuild it" convention (`class-admin.php:106-120` docblock).
- The wallet top-up price table under `bhm-settings` (`class-admin.php:80-92`) is a plain WP `form-table`, correctly deferring to default WP admin styling rather than inventing custom form chrome.

**Rough edge:**
- `render_get_paid_card()` uses an inline `style="border-left:3px solid ...;background:#f6f7f7;padding:14px 16px;margin:16px 0;max-width:760px;"` (`class-admin.php:125`) directly on a `.bhy-alert` class rather than expressing the color/spacing as a `BHY_UI`/`BHY_Style` token. This is exactly the one-off-inline-style anti-pattern the design-system convention calls out — the `.bhy-alert` class exists (suggesting a shared component was intended) but the actual styling (including the money-signal red/green border color) is hardcoded per-instance rather than pulled from a shared success/warning token pair.

## 3. Storefront / collections (`includes/class-storefront.php`)

**Confirmed good / re-confirmed from prior audit (07-13):** the storefront/merchandising layer is genuinely built, not a stub — real taxonomy-backed collections (`bhm_collection`, `class-storefront.php:169-177`), a real collection landing page with auto-generated product grid (`render_collection_page()`, `class-storefront.php:296-310`), a live REST-backed filter block (`rest_query_products()`, `class-storefront.php:469-483`, wired to `storefront-filter.js`), and `BHM_Recommendations::related_products()` (a real content-based scoring model, `class-recommendations.php:24-71`) auto-rendered on every product page via a `woocommerce_after_single_product_summary` hook (`class-storefront.php:93`) — zero-authoring "You may also like" for every product. Spot-checked this pass: still coherent, no dead ends found.
- Empty states route through `BHY_Style::empty_state_html()` when available, with distinct "zero-data" vs. "filtered to zero" messaging (`class-storefront.php:395-405`) — matches the shared empty-state convention the ecosystem audit called out as the single highest-leverage fix elsewhere; this plugin already does it right.
- Self-healing rewrite-rule verification for the collection URL (`add_rewrite()`, `class-storefront.php:203-256`) — throttled re-check + forced flush + explicit object-cache eviction, with debug logging either way. This is invisible to the fan but is exactly the kind of "confirm, don't assume" discipline that keeps a collection page from silently 404ing.

**Re-confirmed known smell (not new) — beige/low-contrast search-input token:**
- The product-filter block's inputs (`class-storefront.php:368-393`, styled at `assets/css/storefront.css:25-28`) do **not** set an explicit background/text color on the `<input>`/`<select>` elements themselves — only the surrounding `.bhm-product-filter` container has `background:var(--bh-surface, #fafafa)` (`storefront.css:25`). Since form controls don't inherit a parent's `background-color` by default, this most likely means these particular filter inputs render with the browser's default white input background, **not** reproducing the beige-on-beige token the prior 07-13 audit found live on the course-catalog and streaming search boxes. This is a code-level read, not a rendered screenshot, so it should be verified live — but as far as the source shows, this plugin's own filter inputs are not obviously carrying the systemic beige-token bug forward. Flagging as "likely not reproduced here, unlike elsewhere" rather than either a fresh confirmation or a clean bill of health.
- Separately, the rest of this plugin's front-end CSS (`assets/css/frontend.css`) consistently uses `var(--bh-*, <dark-theme fallback>)` tokens (e.g. `.bhm-tier-card` at `frontend.css:2`, `.bhm-amount-chip` at `frontend.css:40-44`) sourced from the shared `BHY_Style::inline_css()` system (`class-frontend.php:142`) — this is the correct, non-one-off way to theme a surface in this ecosystem, and it's applied consistently across tier cards, paywall notices, tip jar, PWYW form, and the thank-you banner.

## 4. Gifting (`includes/class-gifts.php`, `[bhm_redeem_gift]`) — new, no prior review

- End-to-end flow present and coherent: gift email captured at add-to-cart (`class-frontend.php:250-262`), visible in cart as a line-item meta (`class-gifts.php:54-59`), a redemption-code email sent on order completion (`create_redemption()`, `class-gifts.php:71-99`), and a claim page (`render_redeem_form()`, `class-gifts.php:111-141`) that handles both the logged-out ("log in or create an account, your gift will still be here") and logged-in claim paths.
- **Good real-time validation instinct**: the claim page checks code validity and already-redeemed status server-side before showing the claim button (`class-gifts.php:117-119`), rather than accept-and-hope.
- **Rough edge — the "Gift this tier" affordance is a `<details>` disclosure, not a first-class action** (`class-frontend.php:250-262`). It's intentionally styled to read as a secondary button per the code comment, but it's still nested behind a click-to-reveal `<summary>` next to two primary "Join"/"Switch" buttons — a fan has to notice and expand it before gifting is even discoverable as an option. For a "new-since-last-audit, zero prior review" feature meant to drive real revenue (someone else's money, on someone else's behalf), a collapsed disclosure is a weaker call-to-action than the primary join buttons sitting right next to it.
- **Rough edge — silent dead end if no redeem page is configured.** `redeem_page_url()` (`class-gifts.php:106-109`) falls back to the homepage if no admin has yet created a page with `[bhm_redeem_gift]` on it. Unlike the tiers-page auto-detect (which the admin settings screen surfaces with an explicit "Not set yet" notice, `class-admin.php:94-101`), there is **no equivalent visibility into whether the gift-redeem page is configured** anywhere in `class-admin.php`'s settings render — an admin who ships gifting without ever creating that page will have every gift email link straight to the homepage with the claim form nowhere on it, and nothing in the admin UI warns them. This is exactly the kind of silent-until-a-fan-hits-it gap the "it just works" principle is meant to catch before it reaches a real gift recipient.
- **Rough edge — no admin-side visibility into gift status outside Debug Tools.** The only place an admin can see recent gift redemptions/claim links is the Debug Tools panel (`class-debug.php:107-121`), which is explicitly a locked, dev-only surface (`OUS_Debug::is_locked()`). There's no real admin screen (e.g., on the Monetization Settings page) showing "gifts sent / pending / claimed" — an artist has no ordinary way to check whether a gift they sold actually got redeemed.

## 5. Pay-what-you-want purchases (`class-frontend.php:465-554`, `class-monetization-ui.php:88-96`) — new, no prior review

- Well-executed anchoring pattern: suggested amount chips scaled proportionally off the item's own floor price (1x/1.5x/2x/3x, `class-frontend.php:499-502`) rather than the tip jar's fixed $5/$10/$25/$50 set, which is the right call since PWYW floors vary per item. Chips set the value but don't replace the manual input (same "chips assist, don't replace" pattern as the tip jar).
- Server-side clamping is real and re-applied at both add-to-cart and cart-recalculation time (`apply_purchase_amount()`/`apply_purchase_price()`, `class-frontend.php:529-554`) — the HTML `min`/`max` are correctly treated as UX hints only, not the actual enforcement.
- Admin-side toggle is a single plain checkbox with clear inline help text ("the price above becomes a minimum instead of a fixed price," `class-monetization-ui.php:96`) — simple, no wizard needed for something this small, appropriately scaled effort.
- No rough edges found in the PWYW flow itself at the code level.

## 6. Subscription pause/resume (`class-frontend.php:270-365`) — new, no prior review

- **This reads as genuinely "branded," not bolted onto WooCommerce Subscriptions' native UI**, matching STATUS.md's claim. It's a real custom form (`render_subscription_controls()`, `class-frontend.php:286-318`) embedded directly inside the fan's own tier card on the `[bhm_tiers]` picker, using the plugin's own `.bhm-btn`/`.bhm-btn-secondary` classes and copy ("Your subscription is paused — you'll keep your account, but supporter access is off until you resume," `class-frontend.php:309`) — not a link out to WooCommerce Subscriptions' My Account screen. This matches the stated "thin wrapper, fan never touches WooCommerce's own UI directly" posture consistently applied elsewhere in this class.
- Correctly gated to only render for a real recurring subscription (checks `wc_subscription_id IS NOT NULL`, `class-frontend.php:280-285`, `320-328`) — never shown for the one-time-purchase-as-30-days fallback, where pause/resume would be meaningless. Good "don't offer an action that does nothing" discipline.
- Server-side ownership verification on the handler is solid: nonce plus an explicit check that `$subscription->get_user_id()` matches the requesting user (`class-frontend.php:343-356`) before any state change — real per-account authorization, not just a nonce.
- **Rough edge — no confirmation step for pausing.** "Pause subscription" is a single-click submit (`class-frontend.php:314`) with no "are you sure" or explanation of what happens next (does access end immediately? does billing actually stop, or just skip a cycle?) before the action fires. Contrast this with the debug tool's own refund-simulation button, which does get a JS confirm prompt (`OUS_Debug::button(..., 'This will revoke your most recently granted test entitlement...')`, `class-debug.php:63`) — the fan-facing pause action, which is the real one with real consequences, has less friction than the internal test tool.
- **Rough edge — testability gap acknowledged but real.** The whole feature is unreachable for QA on any site without the paid WooCommerce Subscriptions extension unless `BHM_MockCommerce` is manually switched on via Debug Tools (`class-debug.php:75-95`) — this is well-engineered (a real mock provider hooking the same `BH_Commerce` filter seams, not a UI-only fake), but it does mean this "branded" control has likely never actually been seen rendered on a live page during this plugin's own development unless someone specifically flipped mock mode on. Worth an explicit live-render check before calling it validated.

## 7. Free trial signup — new, no prior review

- The trial itself is configured entirely in the tier admin metabox (day count, `class-tiers.php:190-195`) and surfaces as a small `<div class="bhm-tier-trial">N-day free trial</div>` badge on the tier card (`class-frontend.php:207-209`) — visible before the fan clicks through, and only shown when WooCommerce Subscriptions is actually active (correctly hidden when the fallback would silently ignore the trial value). No separate "trial signup" flow exists — it's just a modifier on the ordinary "Join monthly" add-to-cart link, which is the right amount of complexity for what this is (WooCommerce Subscriptions' own checkout handles the actual trial-delayed-charge mechanics). No rough edges found; this is honestly scoped rather than under-built.

## Prioritized punch-list

1. **Give the gift-redeem page the same "Not set yet" visibility the tiers page already gets.** `class-admin.php`'s Monetization Settings render currently surfaces whether the tiers page (`bhm_tiers_page_id`) is configured (`class-admin.php:94-101`) but says nothing about `bhm_gift_redeem_page_id`. Since gifting is a real revenue-adjacent feature that silently degrades to "claim link points at the homepage" if unconfigured, add an equivalent status line. Cheap, closes a real "it just works" gap before a real fan hits a dead-end claim link.
2. **Add a confirmation step to "Pause subscription."** `class-frontend.php:314` — a fan-facing action with real billing/access consequences currently has less friction than the internal debug tool's own destructive-action confirm. A simple `onclick="return confirm(...)"` or a two-step reveal matching the gift disclosure's own progressive-disclosure pattern would close this.
3. **Promote gifting from a `<details>` disclosure to a visible action, or at minimum verify live whether the current styling makes it read as equally weighted to "Join monthly."** `class-frontend.php:250-262`. This is a zero-prior-review, new-since-last-audit revenue feature; a collapsed toggle next to two primary buttons risks under-discovery regardless of how well `.bhm-tier-gift summary` is styled.
4. **Pull `render_get_paid_card()`'s inline styles into a shared `BHY_UI` alert/status component.** `class-admin.php:125` — the feature itself (live gateway check) is excellent; the styling is the one clear instance in this plugin of the "one-off inline style instead of a shared component" anti-pattern the design-system convention calls out.
5. **Give admins ordinary (non-Debug-Tools) visibility into gift redemption status.** `class-debug.php:107-121` is the only place this exists today, and it's a locked dev surface — an artist selling gifts has no normal way to check "did they claim it yet."
6. **Live-verify the storefront filter inputs' actual rendered background/contrast**, and separately confirm the subscription pause/resume control has actually been rendered and eyeballed on a real page — both are code-level reads in this pass (Sections 3 and 6) that would benefit most from an actual browser walkthrough before being called fully resolved/validated.

Not reached this pass: `bh-crm`/`BHI_Portal` "Manage your membership" surface referenced at `class-frontend.php:108` (out of this plugin's own scope), and full contrast-ratio measurement of any surface (needs a live render, per the caveat above).
