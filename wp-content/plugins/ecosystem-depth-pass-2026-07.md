## Tier 1 — Named as next in VISION.md's own near-term roadmap, each genuinely close to buildable

### 1a. Role-assignment admin UI
**Gap**: `OUS_Roles` (`own-ur-shit/includes/class-roles.php`) registers granular capabilities and a `bhcore_role_capabilities` filter, but granting one to a non-admin today needs a one-off `add_cap()` call — no UI exists. Confirmed via Explore: `class-debug.php`'s `add_menu()` (add_menu_page + add_submenu_page pattern, `manage_options`-gated) is the page-registration precedent to clone; `BHY_UI` provides reusable table/sortable/search chrome, not a settings-page pattern of its own.

**What makes it magical, not just a checkbox**: the real value isn't "a table of checkboxes" — it's answering "who can act as an instructor/reviewer on this site" in one glance, with the SAME language a site owner already thinks in (bh-courses already needs `bhcore_manage_students`, BH Feedback will need `bhcore_review_submissions` the moment it exists). Frame the UI around **roles-as-jobs** ("Instructor," "Reviewer") rather than raw capability checkboxes — a capability picker under an "Advanced" disclosure for anyone who wants it, but the primary UI is "grant this person the Instructor job," which auto-applies the right capability set. This also means `OUS_Roles::DEFAULT_CAPS` should register a human label/description per capability (small addition) so the UI never shows a raw `bhcore_manage_students` string to the person granting it.

**Execution**: buildable now, no dependency on anything else in this doc. New `OUS_RoleAssignment` class in own-ur-shit — genuinely consider a Debug Tools *section* here (per VISION's own standing instruction that new admin pages default to Debug Tools given the demonstrated `get_plugin_page_hook()` risk on this install), or an Own Ur Shit → Roles submenu tested carefully against that known failure mode first. User list table (reuse `WP_User_Query`), one column per registered "job," toggle per cell, writes via `add_cap()`/`remove_cap()`. No new schema — this is entirely about the missing UI, not new data.

### 1b. Per-notification-type email preferences
**Gap**: `OUS_Notifications::user_wants_email()` is a single flat opt-out, not per-type. The `bhcore_notification_should_email` filter already receives `$type`, so a per-type override can hook in without touching any `notify()` call site.

**What makes it magical**: don't ask a user to manage a settings grid of notification types (that's exactly the "wall for a non-expert" VISION.md's own "it just works" section warns against). Default to the existing single opt-out for everyone; surface per-type control only progressively — "Manage what you get emailed about" link that expands to per-type toggles the first time someone actually wants finer control, with plain-language labels ("Course finished," "Order refunded") not raw type strings.

**Execution**: buildable now. New usermeta (serialized array, type => bool, absent = default-on) read inside the existing `bhcore_notification_should_email` filter callback in `class-notifications.php`. Add the toggle UI to the existing notification inbox panel (`render_portal_panel()`/`render_shortcode()`) — reuses the portal surface that already exists, no new page.

### 1c. Front-end user bar
**Gap**: wp-admin's toolbar is admin-oriented and often invisible to the actual target user (a fan/student/supporter). VISION.md names this directly: notification bell + per-plugin quick links via a filter (bh-courses "continue learning," bh-streaming "now playing," account/logout).

**What makes it magical**: this is the one place in the whole ecosystem that's ALWAYS visible to an ordinary logged-in user regardless of which plugin they're using right now — treat it as the connective tissue that makes six separate plugins feel like one product, not six. The quick-links filter should carry not just a link but a live micro-state (bh-streaming's "now playing" should show the actual track title, not just a generic "Streaming" link) — same "obvious or gone" discipline as the LMS depth-of-magic pass: a plugin only contributes a quick-link when it actually has something live to say, never a placeholder link to "explore courses" for someone not enrolled in any.

**Execution**: buildable now, no dependency on the other Tier 1 items. New `bhi_user_bar_links` filter (same zero-central-registration shape as `bhi_portal_panels`), rendered via `wp_footer`/`wp_body_open`, reusing `OUS_Notifications`' existing bell markup/AJAX. Each of the 4 plugins with a portal panel today (bh-courses, bh-contest, bh-monetization-woo, own-ur-shit itself) is also the natural first registrant of a quick-link.

### 1d. BH Feedback — the biggest lift in this tier, needs its own short design pass before code
**Gap**: entirely unbuilt. `ROADMAP-feedback-and-courses-v2.md` already scopes three tiers (quick-take, detailed written, timestamped-audio annotations), `BHM_Wallet`-backed one-time pricing, a `bh_feedback_request` CPT + `bh_feedback_reviews` table, and `bhcore_review_submissions` sitting scaffolded and unused in `OUS_Roles`.

**What makes it magical**: the roadmap's own v1 scope (quick-take + detailed, audio-annotation tier deferred) is right, but the "it just works" bar here is specifically about the REVIEWER side, not just the submitter side — a reviewer picking up a request needs to feel like using a real tool, not filling out a bare form. Reuse `bh-streaming`'s audio-hash duplicate-detection pattern (`class-audio-hash.php`) directly for "has this track already been submitted for feedback before" — a real, cheap magic moment (flagging a resubmission before a reviewer wastes time on it). The timestamped-audio tier, when it comes, is architecturally the same "pause a step, show an overlay" mechanic just shipped for bh-courses' video annotations this session (`class-render-lesson.php`/`courses.js`'s annotation overlay) — worth explicitly reusing that UI pattern rather than inventing a second one, even though this is a different plugin.

**Execution**: this is a genuinely new peer plugin (`bh-feedback`), the largest single build in this tier. Recommend a short, dedicated design conversation before code — not because the shape is unclear (the existing roadmap doc is detailed and good), but to confirm the reviewer-assignment model (self-serve claim queue vs. assigned-by-admin) and whether `bhcore_review_submissions` should gate the WHOLE reviewer role or just submission-visibility, before the CPT/table schema is locked in. Once that's settled: new plugin scaffold following `bh-courses`' own bootstrap shape (own `class-activator.php`, `class-post-types.php`, wallet-debit hook into `BHM_Wallet`, `OUS_TestRunner` suite from day one per VISION's own "new features get Debug Tools + Test Runner coverage" rule).

### 1e. BH Courses' remaining named gaps (VISION.md's own list)
Four items VISION names together, explicitly flagged as overlapping enough with BH Feedback to design jointly, not separately: **instructor notes** (private, non-student-facing), **discussion/Q&A per lesson**, **cohort/scheduled-release courses**, **instructor-graded steps** (human-reviewed, not auto-scored). The last one is the real overlap with BH Feedback's reviewer queue — a human grading a submitted assignment and a human giving paid feedback on a song are the same underlying "reviewer looks at submitted work, leaves structured feedback" shape. Recommend: sequence this AFTER 1d's design conversation, and use whatever reviewer-queue mechanism BH Feedback settles on as the same mechanism instructor-graded steps use, rather than building two.

Instructor notes and lesson Q&A are simpler, independent, buildable now (private note field on a lesson row = trivial postmeta + capability gate on `bhcore_manage_students`; lesson Q&A follows the exact shape bh-courses already shipped for comments, `class-comments.php`). Cohort/scheduled-release is the one with real depth questions — does drip scheduling (`BHC_Gate::lesson_is_open`) gain a "cohort start date" concept, or is a cohort just a new taxonomy term with its own drip anchor date? Worth a quick scoping conversation, not a full design pass.

## Tier 2 — Marketing tools: VISION.md's own flag that "nothing exists here at all"

Four sub-areas, explicitly named in VISION.md as a category not to let quietly drop:

- **SEO basics** — actually the closest to done: `BH_SEO` (`own-ur-shit/includes/class-seo.php`) already exists and is wired into bh-contest/bh-streaming/bh-courses/public-profile. The real gap is coverage, not infrastructure — confirm registry browse pages and the course catalog both call `set_page_data()` (quick, mechanical, no design needed).
- **Link-in-bio landing page** — VISION's own words: "near-perfect fit... genuinely low-effort relative to value given the public-profile infrastructure already exists." `BHI_PublicProfile` already has avatar/banner/bio/badges; this is mostly a new block type on top of the existing profile page (a linkable-buttons block) rather than a new system. Buildable now, smallest lift in this tier, good first pick.
- **Referral/affiliate tracking** — "who sent a new supporter, was there a discount code, revenue attribution." Naturally lives inside `bh-monetization-woo` given the money angle, and can piggyback on WooCommerce's already-working coupon support (confirmed this session) rather than inventing a discount mechanism — the new part is attribution (a referral code tied to a person, not just a generic coupon) and a revenue rollup, which is a genuinely new small schema (a `bhm_referrals` table: referrer user_id, code, redeemed order_id, credited_at) but no new checkout mechanism.
- **Email broadcast/campaigns** — the largest of the four. VISION explicitly notes `OUS_Notifications`'s email channel is one-to-one/event-triggered, wrong shape for "email everyone in tier X." Needs its own segmented, admin-composed-and-sent concept, reusing `OUS_Jobs` for actual send-out (never a synchronous mail loop — this session's own event-tracking work already fixed exactly this class of bug in bh-contest). Real open design question before code: does a campaign target a live query (tier membership right now) or a snapshot list (who was in tier X at send time)? Worth a quick decision, not a full pass — recommend live query, matching this ecosystem's own "authoritative source, no denormalized counter that can drift" convention used everywhere else (enrollment counts, wallet balances).

**Sequencing**: link-in-bio first (smallest, most self-contained, reuses existing profile infra), then SEO coverage confirmation (near-zero code), then referral tracking (small new schema, clear scope), then email campaigns last (needs the one design decision above, and is the biggest build).

## Tier 3 — Project Tracker / TrackIt parity (bh-crm), Phases B–E

Phase A (reusable checklists) already shipped, via a different, more capable mechanism (`class-subtasks.php`'s full nested-kanban system) than the plan's literal spec — confirmed this session; `PROJECT-TRACKER-TRACKIT-PARITY-PLAN.md`'s own top-of-file status note in `class-projects.php` has already been corrected to say so.

Remaining, in the plan's own recommended order (cheapest first, matching what Explore confirmed about current schema):
- **Phase E (separate scenes/boards)** — cheapest: `bhcrm_projects` has no `scene` column at all today; add it, group `render_boards()` by scene. Real "magic" question: should a scene change ever move a card's context (e.g. archiving a whole scene), or is this purely an organizational grouping? Recommend purely organizational for v1 — matches the plan's own minimal-scope framing.
- **Phase C (stall analytics)** — needs a new `bhcrm_project_card_moves` log table plus a small hook into the existing column-change save paths (`class-subtasks.php::handle_save()`/`handle_toggle()`/reorder handlers) to write it. The magic here is specifically catching a stalled card BEFORE it's obviously a problem — a "hasn't moved in N days" flag surfaced as a visible badge on the card itself (reusing the existing card-rendering, not a separate report page nobody checks), not just a report someone has to remember to open.
- **Phase B (timestamped fixes + feedback log)** — two new flat tables (`bhcrm_project_fixes`, `bhcrm_project_feedback`), rendered as sections on the existing per-card view (`render_projects_section()`).
- **Phase D (Idea Drop / linked local files)** — explicitly the plan's own "least portable" item (linking to local files on someone's machine, not files this ecosystem hosts) — lowest priority in this tier, worth confirming the actual want still stands (a self-hosted ecosystem linking to local-only files is an odd fit) before building.

## Tier 4 — Design Suite Page Manager (the "no special-cased pages" architecture, finale piece)

Confirmed via Explore: **zero of the plan's five phases exist in code** — this is the one item in this whole pass that's genuinely still 100% pure design with nothing to correct or build on top of. `DESIGN-SUITE-PAGE-MANAGER-PLAN.md` already has the phase breakdown (data model → post-edit metabox → context-picker tree UX → default-on for new pages → delete-cleanup hook). This is real, valuable architectural work (the last piece of "collapse every hand-written template into one node tree"), but it's also the most speculative/UI-heavy item in this whole plan and the least tied to a concrete near-term user-facing win compared to Tiers 1–3. Recommend: sequence this last, and treat the existing plan doc as sufficient to start Phase 1 directly (data model) once everything above has landed — no new design pass needed, the doc is already detailed enough to execute against as-is.
